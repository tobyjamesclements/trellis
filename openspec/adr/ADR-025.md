# ADR-025: Accessibility is a release gate

## Status
Accepted

## Context
The product owner requires an accessible user interface. Trellis serves
learners, many of them in public-sector education where the Public Sector
Bodies (Websites and Mobile Applications) Accessibility Regulations 2018
apply, and instructors who author content that must itself be accessible.

## Decision
- Conformance target: WCAG 2.2 Level AA for every Trellis user interface
  (learner, instructor, author, admin, consumer realm), with EN 301 549 as
  the procurement reference and an accessibility statement per tenant.
- Gates: automated checks (axe-core) block merges on any violation; a manual
  screen-reader and keyboard test plan runs per release; QTI interactions
  ship with keyboard-operable alternatives to dragging and pointer gestures
  (WCAG 2.5.7) before they are enabled for authoring.
- Passwordless authentication (magic link, OIDC) satisfies WCAG 3.3.8
  Accessible Authentication by construction; no cognitive function test is
  ever introduced.
- Authored content gets advisory accessibility checks at publish (CAC-16)
  and a tenant policy can make them blocking.
- The design system is built on accessible primitives (React Aria
  Components) rather than restyled native controls.

## Consequences
- Some QTI interactions (graphic gap match, select point) need a designed
  keyboard alternative before they are offered; authoring hides them until
  then.
- Every feature's definition of done includes accessibility acceptance.
- Accessibility findings are severity-1 defects for release.

## Alternatives rejected
- AA "where practical": not a gate.
- WCAG 2.1: superseded; 2.2's new criteria (focus not obscured, dragging
  movements, target size, redundant entry, accessible authentication) are
  exactly the ones an LMS trips on.
