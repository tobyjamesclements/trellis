# ADR-014: Propagation topology: DynamoDB Streams → router → SQS FIFO per partition → updaters; EventBridge for domain events; Step Functions only for long orchestration

## Status
Accepted

## Context
Views need per-partition ordering and single-writer folding; capabilities
need loosely coupled domain events; some workflows wait for humans or run
distributed maps.

## Decision
- Each region's `facts` stream feeds one router Lambda (filtered to fact
  items) that enqueues to SQS FIFO with group `(subject, scope)` for rosters
  and group `partition` for views. FIFO groups serialise per partition;
  batching amortises header writes.
- Updaters publish domain events (`fact.folded`, `view.updated`,
  `effect.ready`, `version.changed`, `cap.exceeded`) to a regional
  EventBridge bus; capabilities subscribe with rules.
- Step Functions Standard is used for: cap reconciliation (24 h wait),
  credential issuance (24 h window), erasure (replication-window wait),
  CC and CSV imports, tenant provisioning, failover, partition recompute
  (Distributed Map). Express is used for short pipelines (publish, export).
- Stability windows ≤ 15 min use SQS delay queues; longer use Step Functions
  Wait.

## Consequences
- At-least-once everywhere; every consumer is idempotent by HWM or
  idempotency key.
- FIFO per-group throughput (~3,000 msg/s batched) bounds a partition's
  fold rate; sharded groups exist for outliers (MVA §hot partitions).
- Stream reads by Lambda are free; SQS and EventBridge costs are small.

## Alternatives rejected
- Kinesis: idle cost per shard.
- Direct stream → updater without SQS: no per-partition serialisation
  across shards; header CAS storms.
