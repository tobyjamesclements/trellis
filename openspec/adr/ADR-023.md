# ADR-023: Automerge for collaborative document scopes; changes stored as facts; the course tree keeps its purpose-built operation log

## Status
Accepted

## Context
The product owner asked for Automerge CRDTs to be considered. Several scopes
in Trellis are documents that people edit concurrently and offline: page and
book bodies, item authoring text, rubric text, learner essay drafts across a
learner's devices, group submissions, and later wikis and glossaries. The
first draft used per-property last-writer-wins for all of them and deferred a
sequence CRDT. Automerge provides JSON-like documents with text (with rich-
text marks), lists, maps that preserve concurrent values, counters, a hash-
chained change graph with per-actor dense sequence numbers, and a
deterministic merge, with a JavaScript package (WASM core) and an official
Java binding (JNI to the same Rust core).

## Decision
- Scopes whose derived state is a document that people edit are **Automerge
  document scopes**: page and book bodies, item authoring and rubric text,
  essay drafts (`_draft#<activity>`), group submission workspaces, and later
  wiki and glossary activities.
- Every Automerge change is a fact of type `am.change.v1`. Automerge's actor
  id is the writer device, its per-actor `seq` is the stream `seq`, its
  change hash is content-addressed like every fact, and its `deps` are
  carried in `refs`. Nothing about the fact log changes: union is still the
  merge, vectors still prove freshness, and the materialised document is
  derived state, recomputable from the changes in any order.
- The server materialises documents with the Automerge Java binding inside
  Java Lambdas; the client uses `@automerge/automerge`. Compacted document
  snapshots are cached as content-addressed blobs keyed by the document
  heads; they are never authority.
- The **course tree** (sections, placements, ordering, node properties)
  keeps the `struct.v1` operation log with fractional ordering keys and
  per-property LWW (CAC-01), because Automerge lists have no move operation:
  a concurrent move of one section by two editors would be materialised as
  two copies. The tree needs moves more than it needs concurrent text merge.
- Automerge's own sync protocol is not used between device and region; the
  Trellis sync protocol (FLS-08) carries the changes as facts. It may be used
  device-to-device in a later change.

## Consequences
- Rich text, drafts and group work merge without loss; conflicts on the same
  map key are preserved and shown, not discarded.
- Documents grow with their history; large documents are materialised from
  cached snapshots plus the changes since their heads.
- Concurrent moves inside Automerge lists (for example reordering items
  within a page) can duplicate an element; materialisation applies a
  deterministic de-duplication by element id and reports it in history.
- The Automerge binary format is versioned by the project; storing raw
  changes as facts means a format change is a re-materialisation, not a
  migration, and snapshots are disposable.
- A native (JNI) dependency joins the backend build and the security supply-
  chain scope (SEC).

## Alternatives rejected
- Automerge for everything including the fact log: a document per
  partition would have to be loaded to fold a single fact, and marks are
  derived, not edited.
- Yjs: excellent for live collaboration but its history is not content-
  addressed and its Java story is weaker.
- Keeping per-property LWW for text: loses concurrent edits, which the
  first draft accepted only because no CRDT had been chosen.
