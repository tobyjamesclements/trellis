# ADR-001: Lambda-only runtime; Java 21 with SnapStart for services, Rust for the derivation engine and hot path

## Status
Accepted

## Context
Trellis must run with no persistent compute, mostly idle, with sharp bursts
at deadlines. The repository is set up for Maven, so a Java toolchain is the
default. Java on Lambda without SnapStart cold-starts in 2–6 s, which is
unacceptable on learner-visible paths (sync, LTI launch). The derivation
engine must run identically on the learner's device (browser) and on the
server, which rules out any implementation that exists only on the JVM.

## Decision
- All compute is AWS Lambda. Step Functions is used only for long waits,
  distributed maps and multi-step imports (ADR-014).
- Service and integration functions are Java 21 with SnapStart enabled,
  memory 512–1024 MB, cold-start budget p50 ≤ 400 ms, p99 ≤ 900 ms.
- The derivation engine is a single Rust crate compiled to `wasm32` for the
  PWA and to a native Lambda (`provided.al2023`) for the server. The view
  updater, NM recompute, intent evaluator, partition recompute and
  anti-entropy functions are Rust because they link the engine and are the
  hot path.
- No provisioned concurrency anywhere. If a Java function misses its cold-
  start budget in measurement, it is rewritten in Rust rather than kept warm.
- arm64 is used wherever SnapStart supports the runtime on it; cost models
  assume x86 as the conservative case.

## Consequences
- Two toolchains in one repository (Maven for services, Cargo for engine and
  hot path). CI runs the golden-vector suite (DRV-02) on both targets.
- SnapStart requires care with randomness and connections at snapshot time
  (uniqueness of seeds, re-established clients in `afterRestore`).
- Cold starts remain visible on the first launch after idle; the product
  accepts this for long-tail usage.

## Alternatives rejected
- Node/TypeScript everywhere with the engine in TypeScript: faster cold
  starts but the server would run the engine on V8 (GraalJS in Java or a
  Node runtime), and determinism across two JS engines is harder to gate.
- Java engine compiled to WASM (TeaVM/CheerpJ): immature toolchain, large
  bundles.
- Containers (Fargate) for the derivation hot path: violates the constraint
  and adds idle cost.
