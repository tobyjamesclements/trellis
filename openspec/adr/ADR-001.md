# ADR-001: Lambda-only runtime; Java 21 with SnapStart for every function; TypeScript and React client; the derivation engine written in TypeScript and executed on the JVM by GraalJS

## Status
Accepted (revised 2026-09-08: the earlier draft assumed Rust for the engine
and hot path; the product owner decided Java on the backend and TypeScript
on the client)

## Context
Trellis must run with no persistent compute, mostly idle, with sharp bursts
at deadlines. The backend language is Java; the client language is
TypeScript. The derivation engine must produce byte-identical results on the
learner's device (browser) and on the server, which rules out two separate
implementations. Java on Lambda without SnapStart cold-starts in 2–6 s.

## Decision
- All compute is AWS Lambda. Step Functions is used only for long waits,
  distributed maps and multi-step imports (ADR-014).
- Every function is Java 21 with SnapStart enabled. No other backend
  language. Native libraries (the Automerge Java binding, ADR-023) are
  bundled as JNI artefacts for the Lambda architecture in use.
- The client is TypeScript with React, delivered as a progressive web app
  (client-platform-and-accessibility).
- The derivation engine is one TypeScript implementation. On the device it
  runs in a Web Worker. On the server it runs inside the Java Lambda under
  GraalJS (the GraalVM JavaScript runtime as a library on the standard
  Corretto JDK), with the Graal compiler enabled through JVMCI where it
  measurably helps; the polyglot context is created at initialisation so
  SnapStart snapshots it warm. Engine code is restricted to a deterministic
  subset of ECMAScript: decimal arithmetic through a pure-JS library, no
  `Math` transcendental functions, no `Intl`, no `Date`, no non-deterministic
  iteration; golden vectors run on V8, SpiderMonkey, JavaScriptCore and
  GraalJS in CI.
- No provisioned concurrency by default (ADR-020). The one budgeted
  exception is the tool-role LTI launch function, which a tenant may
  choose to keep warm at its own cost if measured p99 exceeds 1 s.
- Memory: 512–1024 MB for API functions; 1024–2048 MB for engine-hosting
  functions; cold-start budgets in project.md §5.3.

## Consequences
- One backend toolchain (Maven) and one client toolchain (npm); the engine
  package is consumed by both builds.
- GraalJS in interpreter mode is one to two orders of magnitude slower than
  a JIT-compiled browser engine. Incremental folds are small and fit; the
  partition recompute uses a Distributed Map so wall-clock stays within
  MVA-12's bound even at interpreter speed; JIT via JVMCI is the first
  optimisation if measurements require it.
- Engine-hosting functions have larger snapshots and a p99 cold start up to
  1.5 s; all of them are asynchronous consumers except `derive-explain`.
- The Automerge core is Rust under the hood on both sides (WASM in the
  browser, JNI on the JVM); it is treated as a vendored dependency, not as
  a third implementation language, and its supply chain is covered by
  security-and-assurance.

## Alternatives rejected
- Rust engine compiled to WASM and native (the earlier draft): strongest
  determinism, but a third language on the backend.
- Java engine compiled to JavaScript with TeaVM for the client: keeps one
  source but hands the client team an opaque artefact and depends on a
  small toolchain; kept as the fallback if GraalJS misses its budgets.
- Two implementations with a shared conformance suite: drift is inevitable.
- Node.js Lambdas for engine-hosting functions: would honour "one engine"
  but breaks "Java on the backend".
