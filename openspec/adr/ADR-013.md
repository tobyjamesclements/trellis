# ADR-013: Residency zones: one global table per zone; a small global registry everywhere

## Status
Accepted

## Context
Global Tables replicate every item to every replica region; per-item
replication scope does not exist. Tenants need data residency (EU, US).

## Decision
- A residency zone is a set of 2–3 regions sharing one `facts` global table,
  one set of S3 buckets with bidirectional replication, and per-region
  `derived` tables.
- A tenant belongs to one zone; its facts and blobs never leave it.
- A `registry` global table replicated to every region of every zone holds
  hostname → tenant → zone → region set → home region and feature flags. It
  contains no personal data and is written only by the operator plane's
  provisioning workflow.

## Consequences
- Cross-zone features (a learner enrolled in two tenants in different zones)
  are two separate identities.
- Blast radius is bounded per zone.
- Adding a region to a zone is a global-table replica addition plus derived
  table bootstrap by recompute.

## Alternatives rejected
- One global table worldwide: violates residency.
- One table per tenant: thousands of tables; per-table floor costs; slow
  provisioning.
