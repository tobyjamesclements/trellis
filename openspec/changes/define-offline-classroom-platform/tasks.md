## 1. Transport and hardware spikes

- [ ] 1.1 Assemble the spike rig: a Raspberry Pi 5 with clock battery, one SD card and one NVMe drive, a Windows 10 and a Windows 11 laptop with Chrome, Edge, and Firefox, an Android phone, and a smart plug for power cuts; verify by booting the stock Pi OS image and running a Node and a Bun hello-world binary on it
- [ ] 1.2 Hash-pinned WebTransport: run a minimal WebTransport server on the Pi with a 14-day ECDSA P-256 self-signed certificate and connect from a page served over valid HTTPS on Chrome and Edge using `serverCertificateHashes` against the Pi's LAN address; verify by exchanging messages, rotating the certificate, and reconnecting with the new hash
- [ ] 1.3 Offline service-worker address space: install the spike page as a PWA, make the hostname unresolvable, reopen from the service worker cache, and open the WebTransport connection to the LAN address; verify by recording whether Chrome and Edge connect without a Local Network Access prompt and, if they prompt, what the user sees
- [ ] 1.4 Firefox hash pinning: repeat 1.2 on Firefox; verify by recording pass or fail per Firefox version tested
- [ ] 1.5 Signalling-free WebRTC: run an ICE-lite agent on the Pi with static credentials and a long-lived DTLS certificate (werift and node-datachannel both tried), construct the remote description in the browser from those static parameters, and open a data channel from Chrome, Edge, Firefox, and Safari on any available Apple device; verify by a data channel opening on each browser with no signalling server and by recording setup time
- [ ] 1.6 automerge-repo adapters: wrap the transports that passed as automerge-repo network adapters; verify by passing the automerge-repo network adapter test suite and by a document edited in the browser appearing on the Pi and back
- [ ] 1.7 Pi capacity: load five hundred content documents of mixed size and one log document of two hundred thousand bytes-encoded signed records into automerge-repo on the Pi 5, comparing Ed25519 verification in WASM and in the runtime's native crypto; verify by recording peak memory, load time, and full fold time against targets of under 1.5 GB and under 30 seconds cold fold, and by flagging any target missed
- [ ] 1.8 Power-loss durability: write continuously to the SD card and the NVMe drive through the candidate storage adapters (NodeFS and SQLite) on ext4 and f2fs, cutting power fifty times each with the smart plug; verify by fifty clean boots per configuration with zero corruption of committed documents and by recording which configuration lost the least in-flight data
- [ ] 1.9 Box-as-network: configure hostapd and dnsmasq on the Pi with a captive landing page and a local answer for a project hostname; verify by the Windows laptops and the Android phone joining the Wi-Fi, landing on the page from any typed address, and resolving the hostname to the Pi with the upstream link unplugged
- [ ] 1.10 Certificate path: register a test hostname in a project zone, prototype an acme-dns-style challenge service, and obtain a Let's Encrypt certificate from the Pi over DNS-01; verify by Chrome on Windows loading a page from the Pi's hostname with no warning and registering a service worker, and by a forced renewal succeeding unattended
- [ ] 1.11 Record outcomes: update design.md decisions D12, D13, and D21 and open questions 2 and 7 with the spike results, fix the transport preference order, and choose the storage adapter and filesystem; verify by `openspec validate define-offline-classroom-platform --strict` passing after the update

## 2. Walking skeleton

- [x] 2.1 Monorepo scaffold: packages for the client, the box, the shared core (DSL, fold, share policy, crypto), and the transports, with strict TypeScript, lint, format, unit test runner, and CI; verify by the build and test commands passing in CI on a clean checkout
- [x] 2.2 Keys and signatures: device keypair generation in Web Crypto with Ed25519 and an ECDSA P-256 fallback, algorithm-prefixed key identifiers, sign and verify helpers usable in the browser and on the box, and site key generation on the box; verify by unit tests round-tripping signatures across both algorithms and both runtimes
- [x] 2.3 Site and class logs with the fold: the operation record format (canonical CBOR, signature over the envelope, Lamport clock, per-signer sequence and previous hash), the keyed-set Automerge document, DSL declarations for device admission, class created, started, and stopped, and enrolment added and removed, and a fold with authorisation by role, deduplication, and unknown-operation skipping; verify by property tests showing the same record set folds to the same state in any order, forged signatures are rejected, and unknown types are counted not thrown
- [ ] 2.4 Box binary: the single-file build (Bun compile or Node single-executable, per 1.11) with the embedded shell, HTTPS on the box's hostname, the storage adapter chosen in 1.11, and an LRU document cache; verify by the same binary running on the Pi 5 and on Windows, serving the shell, and preserving data across a restart
- [ ] 2.5 Production transport adapter: the transport chosen in 1.11 as an automerge-repo network adapter with site-key proof and device challenge-response before any sync, and refusal of non-box peers on devices; verify by the adapter test suite passing and by an unauthenticated connection receiving only the join flow
- [x] 2.6 Shell PWA: installable web application with a service worker caching the shell, the IndexedDB storage adapter, persistent storage requested, and every string externalised with English and Spanish for the skeleton screens; verify by the application installing, opening with the network off, and switching language on a device without a reload
- [ ] 2.7 Pi image: a flashable image that boots into the box in box-as-network mode with the captive landing page and a status page showing the setup code; verify by a fresh flash, a boot, a laptop joining the Wi-Fi, and the landing page opening the shell
- [ ] 2.8 Setup and class creation: the setup code admits the first administrator device; an administrator or teacher creates a class and receives its code and short URL; verify by an end-to-end test that creates a class, shows code and URL, and confirms no student device can see it before start
- [ ] 2.9 Join by code: a student device enters the code, registers a display name and PIN or selects an existing name, and the box creates the learner reference, signs the admission and enrolment, delivers a roster snapshot to the teacher device, and emits the QR form carrying the box address, site key fingerprint, and transport parameters; verify by three devices joining, the teacher overview listing three names, and an inspection of the class log finding learner references only
- [ ] 2.10 Start and stop: start makes the code valid and content visible, stop invalidates the code and leaves content readable; verify by an end-to-end test joining before, during, and after
- [ ] 2.11 Collaboration document: a teacher creates a site-tier collaboration in the class, the share policy delivers it to members, three browsers edit concurrently through the box, one edits offline and merges on return, and the teacher locks and unlocks it; verify by an end-to-end test asserting every edit is present after reconnection and that a locked document rejects edits
- [ ] 2.12 Teacher overview, minimal: members with display names and each device's last contact, working from the teacher device's replicas with the box unreachable; verify by an end-to-end test that disconnects the box and still renders the overview
- [ ] 2.13 Unboxing demo: from a boxed Pi 5 and three Windows laptops to a running class with a shared document, performed without documentation in Spanish and then in English; verify by completing the demo in under fifteen minutes each time, recording the timings, and logging every point of confusion as an issue
- [ ] 2.14 Feed back: fold what the demo and the skeleton taught into the specs and design with /opsx:update; verify by `openspec validate define-offline-classroom-platform --strict` passing and by the updated artifacts being committed
